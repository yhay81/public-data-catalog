# 活動価値の再定義

Status: working decision
Date: 2026-07-13
Implementation update: 2026-07-24

## 結論

この活動を、公開データ源の件数を増やす「カタログ作成」から、**データに関する問いを、根拠付きで再現可能な最初の取得まで進める活動**へ再定義する。

一文で表すと、次のとおり。

> AIや開発者が、問いに合う公的データを選び、短時間で再現可能な最初の取得を行い、出典・利用条件・解釈上の注意を保持できるようにする。

`catalog.json` は引き続き重要だが、それ自体を最終成果とはみなさない。今後の価値単位は、情報源の説明に具体的な問い、取得方法、期待される応答、解釈上の注意、検証結果を結びつけた「検証済み取得レシピ」とする。

2026-07-24時点で、5件の取得レシピ、依存なしの安全な実行ツール、応答assertion、単体テスト、週次probeを実装した。これは需要検証の準備が整ったことを意味するが、利用者価値が検証済みであることは意味しない。

## なぜ見直すのか

現状には、次の強みがある。

- 13件すべてに公式ソース、認証、形式、ライセンス、注意点、確認日がある。
- 39件の query hint と39件の caveat があり、単純なリンク集より安全に利用判断できる。
- JSON Schema と依存なしの validator があり、最低限の機械可読性を保てる。
- 5件のレシピが実行可能で、値と出典・利用条件・確認日を同じ結果に保持できる。

一方で、現在のまま件数を増やすと価値より保守負債が増えやすい。

- 対象が「AIまたは人」、分野が世界全体で、誰のどの仕事を改善するかが広すぎる。
- レシピは作者の環境では成功しているが、初見の外部利用者による再現性はまだ検証していない。
- 初期5件は固定質問であり、どの入力を安全にパラメータ化すべきかは未検証である。
- 既存12件の情報源プロファイルは同じ確認日のままで、レシピに接続されない項目の鮮度管理は未整備である。
- 網羅性で競うと、既存の検索エンジン、各国のデータポータル、AIのWeb検索に対する差別化が弱い。

したがって、差別化の中心を「発見」だけに置かず、**選定・実行・信頼・鮮度**を一続きで扱う。

## 対象ユーザーとジョブ

### 第一対象

調査、分析、プロダクト開発の中で公的データを使うAI agentと、そのワークフローを作る開発者。

### 片づける仕事

> 未知のデータに関する問いを受けたとき、追加の基礎調査を繰り返さず、適切な公式ソースを選び、再現可能な最初の結果とその根拠を得たい。

一般読者向けのデータ紹介や、あらゆるデータセットを横断する検索サービスは第一目的にしない。

## 提供価値

| 価値 | 利用者の不確実性 | 提供するもの |
| --- | --- | --- |
| 選定 | この問いにどの情報源が適切か | 対応可能な問い、対象範囲、代替候補との使い分け |
| 実行 | どうすれば最初の正しい応答を得られるか | 境界を絞った取得例、必要な認証、期待する応答形 |
| 信頼 | 値をどう解釈・引用・再利用できるか | 出典、ライセンス、帰属表示、単位、改訂・品質上の注意 |
| 鮮度 | 今も同じ方法で利用できるか | 確認日、軽量probe、変更や失敗の記録 |

## 初期の焦点

当面は、**日本の公的統計・行政データを中心にし、比較に必要な国際ソースだけを含める**ことを推奨する。

理由は、世界中の情報源を横断的に列挙するより利用者と問いを具体化しやすく、既存の `e-Stat` と `e-Gov` を起点に、地域、統計表、分類コード、ライセンスといった実務上の難所に価値を出しやすいためである。天気、地震、地理空間などの既存項目は、具体的な日本向けシナリオに接続できるものを残す。

特定分野の利用者が見つかった場合は、分野特化へさらに狭める。焦点は固定的なブランド定義ではなく、価値を検証するための初期条件とする。

## 成果物の構造

1. **Source profile** — 現在の `catalog.json`。提供者、対象、アクセス、権利、注意点を管理する。
2. **Retrieval recipe** — 具体的な問い、選定理由、実行可能な最小クエリ、期待する応答形、解釈方法を管理する。
3. **Probe result** — エンドポイント到達性と最小の応答契約を定期的に確認する。大規模取得は行わない。
4. **Decision log** — 採用、保留、廃止、変更の理由を残す。

取得レシピには最低限、次を含める。

- `question` または `use_case`
- 対応する `source_id`
- 適用範囲と選定理由
- copyable または executable な最小リクエスト
- 認証情報を外部から渡す方法
- 期待するHTTP status、content type、主要フィールド
- 単位、コード体系、欠損、改訂などの解釈上の注意
- 引用・帰属表示と公式ソース
- `last_verified` と検証結果

## 成功の測り方

件数を主要KPIにしない。最初の30日間は、以下を仮の成功基準とする。

- 代表的な5つの問いに対して取得レシピを作る。
- 初見の利用者または別のAI agentが、追加のWeb検索なしで80%以上のレシピを実行できる。
- 認証不要レシピはclone後2分以内、将来追加する認証ありレシピは認証準備後5分以内を目標にする。
- 全レシピで出典、利用条件、期待する応答形、確認日を欠損なく保持する。
- 公開エンドポイントを使うレシピには、負荷を抑えたprobeまたは明示的な手動確認手順を用意する。
- probe失敗時に、データ源の停止とカタログの不備を区別して記録できる。

実装だけで達成できる項目は完了した。残る主要検証は、5人または5つの独立したAI agent sessionでの実行成功率と所要時間である。

将来、実利用を観測できるようになった場合の北極星指標は、**レシピを使って再現できた有効な取得シナリオ数**とする。

## やめる・続ける・始める

### やめる

- 利用シナリオのない情報源を、分野の穴埋めだけを理由に追加する。
- READMEの掲載件数や分野数を成長の中心に置く。
- 公式文書を要約しただけで、利用可能性を検証済みとみなす。
- 保守方法を決めずに、変わりやすいレート制限や仕様を断定する。

### 続ける

- 公式ソースを優先する。
- ライセンス、認証、出典、品質上の注意を構造化する。
- 推測を避け、不確実性を明記する。
- 秘密情報や大規模な生データを保持しない。

### 始める

- 追加候補ではなく、代表的な問いから調査を始める。
- 最小クエリを実行し、期待する応答契約を確認する。
- 同じ問いに対する情報源の使い分けを記録する。
- 鮮度と保守コストを測り、使われないレシピを廃止する。

## 次の判断ゲート

5つの取得レシピを別の利用者またはAI agentで試した後、次を判断する。

1. 成功率が低い場合、レシピ形式と説明を改善する。
2. 成功率は高いが利用意向がない場合、対象ユーザーまたは問いを狭める。
3. 利用意向はあるが保守負荷が高い場合、対象ソースを減らしprobeを自動化する。
4. 成功率と利用意向がともに高い場合、そのシナリオに近い問いだけを追加する。

このゲートを通るまでは、カタログ件数の拡大を優先しない。
